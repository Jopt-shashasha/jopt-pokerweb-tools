# 業務ポータル — 共通基盤

案A（検索中心・元の黒緑配色）をベースにした独立システム。既存AIFACT・drop・3つの原型には書き込みません。フロントエンドは共通APIを呼び出し、保存・権限・検索をUIから分離しています。

## ローカル起動

Node.js 22.19以上を使用します。

```powershell
cd D:\GitHub\jopt-pokerweb-tools\web\gyomu-portal
npm ci
npm run import:drop -- "D:\JOPT work\業務ポータル\既存資料バックアップ\2026-11-16"
npm run dev
```

`http://127.0.0.1:8788` を開き「このPCの開発環境を開く」を押すと、ローカル管理者として検証できます。**本物のGoogleログインではありません。** このモードは127.0.0.1だけにバインドし、外部公開に使用しません。

会社のGoogleアカウントによる実機検証では、ポータル専用のWeb OAuthクライアントに `http://127.0.0.1:8788/auth/callback` を登録し、未追跡の `.env.local` に `GOOGLE_CLIENT_ID`・`GOOGLE_CLIENT_SECRET` を設定します。設定後は「Googleでログイン」から通常のOIDC認証を行えます。Googleの本人確認と開発用ログインは別経路です。公開環境ではHTTPSと専用の本番リダイレクトURLを使用します。

データは `.local/portal-local.sqlite`、ファイルは `.local/blobs/` に保存。サーバー再起動でも資料・分類・作成者・收藏が残ります。これらと `.env*` はGit対象外です。

## 大会分類・補足タグ・本文検索

大会タグは「共通 / JOPT / SPADIE / U-30 / 戦国 / JOPT GAMES」。同じ資料に複数の大会タグを付けられ、各大会の一覧から同一資料を開けます。開催地・季節はタグごとに指定。JOPT・SPADIEはTokyo / Fukuoka / Osaka / Sapporo、戦国は春 / 秋を初期設定。開催年・開催回は任意。子分類追加は管理者のみです。

既存133件はAIがタイトル・登録済み説明・文脈から一度だけ見直し、判断を `.local/reports/event-classification-reviewed-20261117.json` に保存します。タイトル分類プログラムは削除しました。`node --import tsx scripts/apply-event-review.ts <review.json>` は判断済みデータの検証のみ、`--apply` で変更分だけ適用します。ID・タイトル・元サービス・バージョン・変更前分類が合わなければ全体を停止。資料の作者・原URL・画像・原カテゴリ・説明・共有状態・原更新日は保持し、重複資料は作りません。変更前DBは `.local/backups/`、適用結果はレビューJSON横の `-applied.json` に保存します。

AIに登録を依頼した場合は、そのAIが分類します。MCPの `portal_registration_options` で現在の選択肢を取得し、制作中の文脈から `events: [{event, event_scope_id}]` と補足タグを提出します。資料本体の内容を命令として扱いません。ポータルは分類の存在・組み合わせ・重複を検証し、タイトルから分類を推測せず、バックグラウンドのLLM呼び出しもしません。この選択肢APIは設定済み分類名だけを返し、人物・資料・私有タグ・件数は返しません。旧クライアント用の単一event欄は互換用で、通常の編集で既存の複数分類が消えないよう維持します。

資料ページの「フィルター」で部署・資料種別・元カテゴリ・開催地と大会タグ・補足タグを指定できます。大会タグは複数選択時OR、補足タグはAND。条件をチップ表示し、個別解除・全解除に対応。件数・候補タグ・検索結果は現在の閲覧権限に従います。

タグは任意です。閲覧可能な既存タグを候補に出し、全半角・大小文字・余分な空白による重複を正規化します。意味が違うタグを自動統合せず、少数の検索同義語（Ticket / チケット等）として扱います。未公開・私有資料のタグや件数を他の社員へ表示しません。

検索はタイトル・用途・作成者・分類に加え、保存済みHTMLの可視テキスト、取り込み済みAIFACTの説明、添付MDの本文を対象にします。HTMLのスクリプトは実行しません。既存リンク先の本文は自動取得しないため、URLだけの資料は登録済み情報の範囲で検索します。検索用本文は資料ごとに最大120,000文字。索引の作成・検索にLLM呼び出しはありません。

## 原本URLの登録

手動登録とMCPの登録はいずれも、公開・共有済みのHTTP(S) URLが必須です。作成者がChatGPT SitesやGoogle Drive、GitHubなどにHTML・PDF・README・ツールを置き、原本のURLを登録します。原本の閲覧権限は共有元で設定します。ポータルにはURL・用途・分類・タグなどを保存します。READMEも原本URLとして登録でき、短い利用案内は用途欄に書けます。

`node --import tsx scripts/verify-discovery.ts` は独立検証DBで、実MCPクライアントからのURL登録、ブラウザ確認、用途の検索、原本URLの取得を確認します。

## 既存資料のプレビュー

過去に保存済みのHTMLとMDは、資料の閲覧権限に従って引き続き閲覧・取得できます。旧HTMLのプレビューはsandbox付きiframeとCSPで分離します。

縮略図は一覧と詳細ページに常時表示し、詳細ではクリックして拡大できます。移行済みの元画像を優先。画像がない場合は、保存済みHTMLまたは添付MDの内容から初回表示時にプレビューを生成・保存します。原文変更時だけ再生成し、通常表示にLLM呼び出しはありません。対象本文は5 MiB以下。生成できない場合は自動カバーを表示します。

`src/preview-renderer.ts` は別プロファイルのヘッドレスChromiumでファイル内容だけを描画します。JavaScript・外部通信・Service Worker・ダウンロードを無効化し、社員のブラウザ・Cookieへ接続しません。動的なJS画面や外部画像・外部CSSは反映されません。レンダラーの実行パスは `PORTAL_CHROMIUM_PATH`、未指定時はWindowsのインストール済みChromeまたはLinuxの `/usr/bin/chromium`。本番ホストでも利用可能な実行環境が必要です。

`scripts/backfill-previews.ts --apply` で保存済みファイルのプレビューを補完できます。`--proposal-file <path>` は元DROPのSHA-256と一致する企画書HTMLだけをプレビュー入力として保存し、元URL・共有状態は変更しません。外部URLだけの資料は自動取得せず、原画像がなければカバー表示。PDF・Office原稿の変換や、URL先の自動撮影は未対応です。

## 本番接続に残る設定・実装

### Token消費の扱い

RSS取得・キャッシュ・SQL検索・PICK UPにLLM呼び出しはありません。社員ごとに常駐AIを動かしません。連携用コンテキストAPIは資料候補3件・ニュース2件、応答全体6,000 bytes以下に制限し、元ファイル一覧・所有者の内部情報・長文の原メタデータを含めません。これはモデルごとの正確なToken上限ではありません。モデルへ渡した結果は入力Token等の使用量に含まれます。

「当日最初の実利用時だけ確認」「同じ候補を再通知しない」「本人のCodex側で既存の関連コンテキストを使って選ぶ」は推奨設計で、社員のCodex設定・Hooks・記憶にはまだ変更を加えていません。全会話履歴の収集・定期的なAI推薦ジョブも実装していません。

1. ホスティング先の決定。現在はローカルNodeサーバーであり、Sites/Cloudflareへ公開済みのシステムではありません。Worker環境ではDBの非同期アダプター・ファイルストレージ・認証方式の適合確認が必要です。
2. 新ポータル専用Google OAuth設定。`.env.example` を参考に環境変数を設定し、`APP_ORIGIN/auth/callback` を登録。旧dropのクライアントシークレットやセッションを流用しません。
3. Googleで本人確認できた `xiao.h@japanopenpoker.com` を初回管理者に設定。他の社員は検証済みGoogle subjectとインポートした所有者情報を照合します。
4. Slack通知先・発行者のSlack ID・GitHub権限連携。画面入口は残していますが、現在は送信・招待を行いません。アクセス申請APIは未接続を503で返し、成功扱いにしません。
5. Codex向けローカルstdio MCPを実装しました。検索・資料取得・リンク登録は、MCPが作る依頼ページをログイン中のブラウザで実行し、MCPで結果を受け取る方式です。Google本番ログインを使った検証は引き続き必要です。リモートHTTP MCPは下記の実装を参照してください。

### 効果の一行（任意）

登録時に「誰が使う・どの作業・前・後・頻度」を任意で入力できます（Web登録フォーム、MCPの `portal_register_link` の `impact`、編集画面）。サーバーが固定テンプレートで「カスタマー担当向け｜Voucher照合ツール」「Voucher照合が 5分/件 → 30秒/件（1日20件）」の見出しを作り、一覧・PICK UP・詳細・MCPの検索結果（`headline`）に表示します。LLM呼び出しはありません。前と後の片方だけでは比較を表示しません。AIには数字を推測で作らないよう指示しています。編集時に `impact` を省略すると既存値を保持し、`null` で削除します。誰が使う・どの作業は検索対象です。Slack紹介文もこの見出しを使う予定です。

### Slack紹介・週次まとめ

管理者が内容と送信先を確認してから、1件ずつ部署の普段のチャンネルへ送ります。自動送信・定期送信はしません。`SLACK_BOT_TOKEN`（`xoxb-…`、`.env.local`）が未設定ならプレビューのみです。

- 送信先：部署ごとのチャンネルIDを「Slack連携」（管理者）で設定し、チェックを入れた部署だけに送信可能。`node --import tsx scripts/apply-slack-channels.ts docs/slack-channel-map.json --apply` で確認済みIDを取り込めます（部署名が一致しなければ停止。送信は有効化しません）。
- 対象：送信時点で「共有中・社内共有」の資料だけ。文面は効果の一行（なければ用途の最初の文）、作成者、「使い方を見る」ボタン。「AI」の宣伝ラベルは付けません。
- 重複・頻度：同じ資料を同じチャンネルへ二重送信しない。1チャンネル直近7日で2件まで。管理者は注意を確認したうえで上書き可能。
- 送信結果：タイムアウト・5xxは `unknown`（結果未確認）として記録し、自動再送しません。管理者がSlackを確認して「届いていた／届いていない」を確定するまで、同じ紹介は送れません。
- 週次まとめ：日本時間の直近7日の新着（最大5件）と、Codex読み取り＋リンククリックが最も多い1件。期間ごとに1回。
- 個人DM：「Slackで紹介」→「個人にDM」で、選んだ社員（1回30人まで）に1対1で送れます。SlackユーザーIDは会社メールで照合して保存（`users:read.email`・`im:write`）。同じ資料を同じ人へ二重に送らない、1人あたり直近7日3件まで（管理者は確認のうえ上書き可）。DMはチャンネルの上限に数えません。
- テスト送信先：「Slack連携」でテスト用チャンネルIDを入れると、チャンネル紹介・DM・週次まとめはすべてそのチャンネルだけに届きます（DMは「本番ではこの人たちに送る」と表示）。テスト中は重複・上限は注意表示のみ。「テストを終了」で部署チャンネルへの送信に戻ります。
- AIニュース：ポータルのニュース欄（ML_Bear Timesの新機能・新ツール記事）から管理者が選んで（1回5件まで）ニュース用チャンネルへ送ります。送れるのは現在のフィード上の記事だけで、見出し・115文字までの要約・出典リンクのみ（本文は転載しません）。同じ記事を同じチャンネルへ二重に送りません。週次まとめに「今週のAIニュース」（3件まで）を入れる設定もあります。Codexへのお知らせ（新着資料・ニュース）は**PCごとに週1回**（管理者が「1日1回」に変更可、週は日本時間の月曜始まり）。頻度はサーバーが判定し、それ以外の会話では `portal_whats_new` が `{"skip":true}` だけを返すため、トークンはほぼ消費しません。お知らせ時もタイトルとリンクだけの短い形式です。Codexの定期タスクは使いません（毎回フルのAI実行になり、かえって消費が増えるため）。ニュース一覧は `portal_news` で取得できます。
- 計測：「使い方を見る」は `/go/<資料ID>?p=<送信ID>` で人のクリックだけを記録し、必ずポータル詳細へ移動します（クエリのURLへは飛ばしません）。Slackの展開・ボットは数えません。ポータルが127.0.0.1の間は同僚が開けないため、設定でリンク先を「元の資料」にできます（その場合クリックは記録されません）。クリック数・読み取り数は参考値で、業務での実利用回数や削減時間を示すものではありません。

### Codex連携（リモートMCP・ワンクリック設定）

部署でCodex/OpenAIアカウントを共有していても、ポータルは社員本人の権限で動きます。本人の識別はCodexアカウントではなく、ポータルが発行する**本人専用の連携トークン**で行います。

1. ポータル右上「Codexと連携」→「Codexで設定を開始」。`POST /api/codex/setup` が10分間・1回限りの設定コードを作り、`codex://new?prompt=…` でCodexの新規会話を開きます（入力欄に入るだけで自動送信はしません）。開かない場合は設定文をコピーします。
2. Codexが `irm '<origin>/setup.ps1?code=…' | iex` を実行。スクリプト（`src/codex-setup.ps1`）はコードを `POST /setup/exchange` でトークンに交換し、ユーザー環境変数 `JOPT_PORTAL_TOKEN` に保存、`~/.codex/config.toml` に `[mcp_servers.jopt-portal]`（`url=<origin>/mcp`・`bearer_token_env_var`）、`~/.codex/AGENTS.md` に「作業前にポータルを検索する」ルールを追記し、`/setup/whoami` で確認します。既存ファイルは `.bak-日時` に保存し、マーカー区間だけを置き換えるため何度実行しても重複しません。トークンは画面・プロンプト・URLに出しません。
3. Codexを再起動すると `/mcp`（Streamable HTTP、JSON応答）に接続します。

| ツール | 動作 |
| --- | --- |
| `portal_search` / `portal_read` / `portal_registration_options` | トークン所有者の閲覧権限で直接実行（ブラウザ不要）。`portal_read` は `resource_usage` に利用記録 |
| `portal_whats_new` | 前回確認以降の社内共有の新着（本人の部署を優先・最大5件）。同じ項目は再通知しない |
| `portal_register_link` / `portal_result` | 登録は従来通りブラウザで確認・実行。依頼はトークン所有者に紐付き、本人のブラウザ以外では実行不可 |
| `portal_whoami` | 接続中の社員を確認 |

トークンは読み取り＋登録依頼の作成のみ。有効期限90日、サーバーにはハッシュのみ保存。同じPC名で再設定すると旧トークンは失効し、「連携中のPC」から本人が解除できます。アカウント無効化で即時失効。`/mcp` は他オリジンからのブラウザ要求を拒否します。

既知の制約：スクリプトはWindows PowerShell 5.1向けで、実機（Codex for Windows）での確認が必要です。`codex://` はCodexデスクトップアプリ専用で、CLI・IDE拡張の利用者はコピーで設定します。ローカル開発（127.0.0.1）では本人のPCでのみ試せます。社員が使うにはHTTPSで公開されたポータルが必要です。従来のローカルstdio MCP（`src/mcp.ts`）もそのまま使えます。

### 本番運用：待ち受けアドレスとバックアップ

本番（`npm start`）は `HOST` で待ち受けアドレスを指定できます。VPSでCaddyの後ろに置くなら `127.0.0.1`（既定）、コンテナ／Flyでは `0.0.0.0`。ローカル開発は常に `127.0.0.1` です。

`node --import tsx scripts/backup.ts --out <BACKUP_DIR>` は、SQLiteのオンラインバックアップ（WAL内の未反映分も含む）を単一ファイルで保存して整合性を検査し、未コピーのBlobを追加コピーします。既定で14世代保持。データディレクトリの内側には保存できません。cronや定期ジョブで毎日実行し、保存先はサーバー／Volumeとは別の場所にしてください。

### ブラウザのログイン保持

ログイン後はHttpOnlyの永続Cookieを利用し、ブラウザを閉じても保持します。30日間未使用で期限切れ。利用中は最大1日1回更新し、最終更新から30日、初回ログインから最大90日まで保持します。ログアウトは現在のブラウザのサーバー側セッションも削除し、別ブラウザのログインは保持します。無効化されたユーザーは既存セッションでも利用できません。旧1時間セッションは、有効なうちにアクセスした場合だけ新しい保持期間へ移行します。

保存単位は端末の物理IDではなくブラウザのプロファイルです。Cookieの削除・プライベートモードではログインを保持できません。セッション秘密値をlocalStorageやCodex設定へコピーせず、サーバーにはハッシュだけを保存します。本番CookieはSecure・HttpOnly・SameSite=Lax・__Host-付きです。

Codexで同じブラウザを操作する際は、そのブラウザのポータルログインで権限を判定します。Codex/OpenAIアカウントとの紐付けはありません。MCPはCookieを取得せず、ブラウザでの実行後に依頼単位の結果だけを取得します。Googleログインは本番接続設定後に実機で確認が必要です。

### ローカルMCPの使い方

`src/mcp.ts` は公式MCP SDKのstdioサーバーです。起動・ツール一覧の取得にはポータルログイン不要。`portal_search`・`portal_read`・`portal_register_link` は10分間有効の依頼URLを返します。Codexのブラウザ機能でURLを開き、表示された現在のアカウント・操作内容を確認して実行したあと、`portal_result` で結果を取得します。ブラウザ機能がない環境では利用者が依頼URLを開く必要があります。自動的にブラウザを開く常駐処理・ブラウザからのCookie抽出は行いません。

リンク登録の初期値は「自分だけ・下書き」。管理者の作成者指定は既存のポータル権限を使い、実際の操作アカウントは別に記録します。同じ依頼の再実行で登録を重複させません。登録と結果保存は一つのDBトランザクションで確定します。

実行結果の取得用秘密値はMCPプロセス内だけで保持し、モデルには返しません。サーバーにはハッシュを保存。実行にはブラウザの通常のセッション・Origin・CSRF検証が必要です。実行後の結果取得もそのセッションの有効性を検査し、ログアウト時は当該依頼結果を削除します。依頼作成・結果取得用の匿名APIからは資料操作を直接実行できません。

検索は1回5件まで、結果は16,000 bytes以下。外部URLの本文を代理取得する機能ではなく、ポータル上の説明・原本URLを返します。GitHub・Drive等の原本権限を変更・迂回しません。常駐するAI、モデルAPI、ニュースの定期ポーリングはありません。結果をCodexへ渡した分は通常の入力Tokenに含まれます。

検証用スクリプトは `node --import tsx scripts/verify-mcp.ts`。`http://localhost:8790` に実dropデータを使う独立テスト環境を起動し、実MCPクライアント経由で検索・読み取り・非公開下書きの代理登録を順に検証します。テスト結果は `.local/mcp-browser-qa-*/verification.json` に保存し、通常環境の資料には書き込みません。

本番モードは `npm start`。HTTPSの `APP_ORIGIN` と明示的な `PORTAL_DATA_DIR` が必須で、ローカルモードとは別DB `portal.sqlite` を使用します。本番へ導入する場合は環境変数を設定して `npm run import:drop -- <backup-path> --production`。本番サービスの起動・公開・権限設定はまだ行っていません。

## 发布前必须完成

1. 执行 `node verify-baseline.cjs`，确认线上导出基线没有变化。
2. 重新查看 Cloudflare Active deployment。只有仍为上述版本时，才能将它作为本次更新的父版本；如已被其他人更新，停止发布并重新导出最新版本。
3. 保存最新普通变量、绑定、定时触发器、资源和密钥名称清单。不要修改现有密钥或把密钥值提交 GitHub。
4. 取得 D1 的恢复点或导出，并盘点 Appwrite 文件。数据备份必须记录时间与范围；本代码包不代表数据备份已完成。
5. 当前 ASSETS 静态文件版本需要保留，或在发布前独立导出验证；不能用本机旧前端构建覆盖它。
6. 在独立的候选版本中实现 R2 配置开关、仅指定 LINE 用户写 R2、跨存储读取和撤回处理。普通玩家继续写 Appwrite。记录基线与候选版本的逐文件差异。
7. 完成候选版本测试，确认关闭 R2 测试开关后，测试期间写入 R2 的图片仍可读取。
8. 在本地发布记录中写明：父版本、新版本、操作者、Asia/Tokyo 时间、开关值、测试账号、验证结果及回退目标。

## 回退分两种情况

### 尚未向 R2 写入任何新数据

在 Cloudflare Worker → Deployments，将发布前保存的原版恢复为 100% 流量，并核对绑定与普通变量。随后检查客服页面、收图、历史图、FAQ、Slack 通知及定时重试。

### 已有新图片写入 R2

不能直接退回只读 Appwrite 的原版，否则新图片可能无法访问。

优先关闭 R2 测试开关，把新写入切回 Appwrite，同时保留已经验证的兼容读取版本和 R2 绑定。这是第一层回退。

如果必须完整退回原版，先停止向 R2 写新图，按原 storage_key 将切换后仍有效的图片补到 Appwrite，并核对文件大小、内容校验值和 D1 引用。确认撤回或取消的图片不会被恢复、全部有效图片都能由原版读取后，才恢复原版为 100% 流量。

## 数据边界

- 回退 Worker 版本不会自动回退 D1、R2、Appwrite 或 Durable Object 数据。
- 不得为了回退代码，恢复旧 D1 快照并覆盖期间新产生的客户咨询。
- 历史迁移只复制仍有效的文件，不重放客户 Webhook，不自动补发客户消息或 Slack 通知。
- 在验收和保留期结束前，不删除 Appwrite 原始文件；R2 测试也不修改正式 LINE Webhook。
